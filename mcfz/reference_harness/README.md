# Reference Harness

A minimal, self-contained example of an MCFuzz harness. It links **no external
libraries**: instead of calling a real cryptographic library, it calls its own
stand-in "library" ([`dummy_lib.c`](harness/dummy/dummy_lib.c)) that contains a
deliberately **non-constant-time** primitive. Use it to try MCFuzz end-to-end
and as a template when writing a harness for a real target.

## What it demonstrates

The stand-in library implements a toy stream cipher whose key is (by default)
secret. Its `dummy_cipher_encrypt` contains two independent constant-time
violations, both driven by the secret key:

1. **Key-dependent branch** — the direction of a bit rotation depends on a key
   bit, so the executed instruction sequence differs between two keys. MCFuzz
   reports this as an **I-type** (control-flow) leak.
2. **Key-indexed table lookup** — a substitution table is indexed by a key byte,
   so a load address depends on the key. MCFuzz reports this as a **D-type**
   (data-access) leak.

## Layout

The harness itself is a single translation unit; only the stand-in library is
kept separate, mirroring how a real harness links against an external library.

| Path        | Role                                                                                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------- |
| `libdummy/` | The stand-in "external library": its own source, public header, and Makefile. Contains the non-CT primitive. |
| `harness.c` | The whole harness: CLI, policy/input parsing, deterministic stack, and the cipher glue that calls libdummy.   |
| `harness.h` | Harness data types and the `start_harness` entry point.                                                       |

The harness includes only the library's public header
(`libdummy/dummy_lib.h`) and links against the compiled archive
(`libdummy/build-*/libdummy.a`) — just as it would with a real third-party
library.

## Building

```bash
make -C mcfz/reference_harness
```

This builds the stand-in library (via `make -C libdummy`) and links it into two
harness binaries:

* `harness-native` — non-instrumented, built with debug info; used by
  MCFuzz's tracing stage (config key `bin_native`).
* `harness-afl` — AFL++-instrumented; used by the input-generation
  stage (config key `bin_instrumented`).

The library is compiled once per configuration (native and AFL) so the code
under test is instrumented in the AFL build. The AFL build expects AFL++ under
`~/.local/afl` (the quick-start default); point it elsewhere with
`make AFL_ROOT=<dir>` (e.g. `make AFL_ROOT=~/bin/AFLplusplus`). Build only the
native binary with `make native`.

## Running the harness directly

```
harness-native -d <input> -p <policy> [-o <ciphertext>]
```

* `-d` — input blob generated by the fuzzer.
* `-p` — policy file.
* `-o` — optional file to receive the ciphertext.

The input-blob layout, the ratio split, and the policy-file syntax are the
standard MCFuzz harness contract; see
[The Fuzzing Harness](../../docs/mcfz/harness.md) for their full description.
This harness follows that contract with a three-field policy:

```
key: private
iv: public
plaintext: public
```

With this default policy the key is secret, so both leaks in the dummy library
are reported. Marking the key `public` instead makes the harness effectively
constant-time with respect to secrets, and MCFuzz reports nothing.
